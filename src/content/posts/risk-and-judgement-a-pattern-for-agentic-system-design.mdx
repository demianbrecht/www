## Is this thing on?

I have a tendency to make assumptions about my target audience at times: *If this makes sense to me objectively, it must be true for everyone else, **right***? Well, I hate to break it to myself, but that is actually very rarely the case. This has been surfacing at a noticeable rate recently when I talk about my approaches to agentic system architecture. Over the years, I've learned to start looking inward ("how am I miscommunicating this?") rather than outward ("how can they *not* understand this?").

When developing an agentic system, the design approach that I've been taking has become a pattern loosely based on traditional threat modelling. To me, threat modelling makes sense to apply to agentic systems because I treat unbounded agents as potential adversaries to the system they're part of.

This blog post is an attempt at describing the approach and proposing a reusable pattern when it comes to agentic development so we can start from the same fundamentals when speaking about more complex system implementations.

## What problem are we trying to solve?

Ever since I encountered my first instance of "Sorry, you're right. I should have...", I wondered how we would actually trust non-deterministic systems like LLMs in critical cases where we absolutely needed deterministic behaviour. I also grew in awe of the increasing number of seemingly deterministic bash scripts that were being encoded in prose fed to an LLM. Not only is it costly, but just because it's in prose doesn't mean that the LLM is guaranteed to observe it.

This realization (and further research) led me to the conclusion that developing agentic systems against a spectrum from entirely deterministic to purely non-deterministic was the best way forward ([Stop Asking LLMs to be Deterministic](/posts/stop-asking-llms-to-be-deterministic)). The pattern proposed in this post clarifies my approach to determining what goes into software and what should be owned by an LLM. The overarching pillars of this design are trust and cost.

## Sketching it out

When designing an agentic system, one of the first questions is: [who should own the control loop](/posts/the-division-of-the-local-harnesses/#who-owns-the-control-loop). Some functions require interpretation, investigation or adaptation. Others can follow explicit rules. Some mistakes are inexpensive and reversible. Others can cause a SEV-0 and impact customer trust. This is not a holistic classification, but rather a classification of each individual function that is required to achieve the holistic goal. They should influence how the division of responsibility is split between software, agents and humans.

A useful starting point is to decompose your problem into isolated functions. Take an automated bug fix as an example.

High level: *Fix this bug* <br/>
Decomposed:<br/>
  - Clone the target repo
  - Investigate the bug
  - Propose or make the fix
  - Run static analysis
  - Execute runtime QA
  - Push a PR
  - Review and iterate on PR
  - Merge

This gives you a starting point for the system you're designing.

Like traditional software development, the design process is iterative and should not be carved in stone. It should be iterated on as you collect real-world signals based on usage.

```
Decompose the work
  -> identify judgement requirements and possible failures
  -> establish tolerances and verification
  -> propose an allocation and controls
  -> evaluate workflow composition and residual risk
  -> accept or revise
```

The outcome of this stage of the process is to have a clear picture of every logical function that we can then map the next stage against.

### The axes of the agentic architecture model

Now that I have the logical functions in my design fleshed out, I can use these two axes to determine who should own each one (software, a model, or a human):

- **Judgement requirements**: Does this particular function require human-like judgement? Another way to think about this is: pre-LLMs, is this something that I would have automated in a script or something that would have genuinely needed me to complete?
- **Risk**:
  - *Concerns*: What are the possible failures, the likelihood, their consequences and the resources exposed?
  - *Tolerance*: Are the concerns tolerable? Do we actually care?

If you squint, the two axes are the two pillars. Judgement is about cost: if a function doesn't need it, an LLM is the expensive way to do it, in tokens, in latency, and in the odds that it ignores the instruction. Risk is about trust: how much of it you can afford to extend to this function.

The two axes produce a useful matrix to assist in classifying each function:

| | Low judgement | High judgement |
|---|---|---|
| **Low tolerance** | Software. Write the script and enforce the rules. | The agent contributes judgement inside hard limits, with verification or a human deciding before anything consequential happens. |
| **High tolerance** | Still software. It's cheaper and more predictable than prose. | Let the agent explore within an agreed scope. |

Notice the left column: if a function doesn't need judgement, the answer is software regardless of risk. Risk tolerance only decides how much rope the agent gets.

## Digging in

Now that we have the logical functions and the matrix to apply against each function for classification, we go ahead with that stage of the design. While working through each function, you may very well find that the function itself is too broad and needs to be exploded for further analysis.

### Classify the function

Use the above matrix to classify each step of the workflow between software, LLM and human ownership. In either case, a rough set of failure modes should be identified. This is intended to give you a rough idea about what could go wrong. It's not intended to be comprehensive because you're nearly *always* going to encounter unexpected failures.

### LLM-owned threat modelling

In the case of LLM-owned functionality, we need to understand what can go wrong and how it can possibly impact the entire system. Loosely using traditional threat modelling is a great tool for this. Models should be treated as adversarial actors. Not because they're malicious, but because anything that lands in their context (a test log, a README, a web page) can steer them, and you can't predict all of it. Adversarial is the safe default.

Useful questions include:

- What can this function read or change?
- Who or what can influence its inputs?
- What happens if the output is wrong?
- Could an apparently harmless output trigger a consequential action elsewhere?
- How quickly would a failure be detected?
- How reversible are its effects?

Failures should be kept concrete. "The agent made a mistake" is too broad. "A misleading test log causes the agent to send credentials to an external service" gives the design something specific to address.

### Establish tolerances and verification

As the system architects, you and your team are entirely in the driver's seat here. How much do you care if any of the failure modes or adversarial impacts occur? If LLM-owned, what limits do you want to impose on the model (tools, tokens, timeouts, etc.)?

A tolerance is only as good as your ability to enforce and verify it. For each check, be honest about what it establishes and what it misses. A passing test suite provides evidence that the behaviours it exercises work. It says considerably less about requirements nobody wrote down. And the model telling you it's done isn't verification: anything consequential needs a basis beyond the agent declaring its own success. If your checks can't establish what you need, narrow the scope, add a control, or hand the decision to a human.

The act of establishing tolerances may also unearth other functions that need to be added to your system. For example: if a function is high risk but absolutely requires judgement, you might add a second LLM-based function to review the first. That can catch some mistakes, but it's still a model checking a model. It shouldn't be the only thing standing between a low-tolerance failure and production. Pair it with deterministic checks or a human decision.

The point of this stage is to identify risk concerns, tolerances and mitigation plans depending on the classification.

### Propose an allocation of authority and controls

Identify who may:

- **Propose**: Generate a hypothesis, recommendation or candidate action
- **Decide**: Determine whether it should proceed
- **Execute**: Produce the external effect

An agent might propose a patch or write the code. Software might check its permitted paths and run required tests. A human might accept the associated PR and merge it into the system.

The point here is to ensure that the correct guardrail owners are in place for each function.

### Evaluate the composition

Applying the matrix against individual functions is a great starting point for your system. It helps you decide on an implementation strategy for each. However, it doesn't necessarily account for interactions between functions, which is where new risks can emerge.

As a concrete example, let's take another look at three functions of our bug-fix workflow: investigate the bug, make the fix and push a PR. In isolation, these might look fine. The agent investigates and makes changes within its isolated workspace, while software validates the patch and handles pushing the PR. Each function has its own boundaries and controls.

But what if your service depends on an open-source package and the fix needs to be contributed upstream? The agent takes a ticket from an internal work tracker as context, investigates the bug and makes the fix. Software validates the patch and pushes a PR to the public repository.

What happens if the patch or PR description contains information from the internal ticket? You've potentially just leaked internal company information into a public repository. Not a great place to be.

Remember that the agent doesn't have any network access, so it can't send anything out on its own. But it doesn't really need to, because software will happily push whatever the agent wrote. And while there's a human sign-off before the push, that human was signing off on runtime QA, not on what's in the PR description. By the time a human gets around to reviewing the PR, the information is already public.

In this case, none of the individual functions necessarily violated their assigned boundaries. The failure was in how they were composed.

So while individual functions are useful for classification and identifying failure modes, we also need to evaluate the workflow as a whole. This is basically the "could an apparently harmless output trigger a consequential action elsewhere?" question from earlier, just applied to the entire workflow. What information and authority move between functions? Could a series of otherwise acceptable operations produce an outcome we're not willing to tolerate?

If the composition introduces new risks, we need to revisit our classifications, tolerances and controls. In this example, pushing a PR to a public repo isn't really a low judgement function anymore. Someone needs to decide whether the content is safe to publish, and our tolerance for getting that wrong is pretty much zero. Software can scan for the obvious things like ticket IDs, but a human should be looking at what's actually going out before it goes public. Even better, if the work is going upstream, maybe the agent doesn't need the internal ticket at all.



Whatever risk is left after that is the residual risk that you're accepting (or not) in the last step.

## Putting it together: fixing a bug

Back to the bug fix from earlier. Run each function through the matrix and it looks something like this:

| Function | Judgement | Tolerance | Owner | Controls |
|---|---|---|---|---|
| Clone the target repo | Low | Low | Software | Validates the repo and base revision; clones into an isolated workspace |
| Investigate the bug | High | High, within budget | Agent | Tool, token and time budgets; no credentials; no outbound network |
| Propose or make the fix | High | High in the workspace, none outside it | Agent | Can only write to the isolated workspace |
| Run static analysis | Low | Low | Software | Configuration lives outside the agent's reach |
| Execute runtime QA | High | Low | Agent owns the loop, a human gets the [last word](/posts/runtime-qa-give-the-agent-the-loop-not-the-last-word) | Consequential actions need approval |
| Push a PR | Low | Low | Software | Only software holds push credentials, and it pushes the exact patch that passed |
| Review and iterate on PR | High | Medium | Agent proposes, human reviews | Every iteration goes back through static analysis and QA |
| Merge | High | Low | Human decides, software executes | Approval is bound to the exact commit; any change needs fresh approval |

As a flow, it looks like this:

Then try to break it:

- A test log tells the agent to upload environment variables. It might even try, but there's nothing to upload and no network to send it over.
- The agent burns through its budget. The next tool call is refused, and restarting doesn't reset the clock.
- The PR changes after it's approved. The approval no longer applies.
- A plausible but wrong patch passes every test. Our automated checks haven't established enough confidence to permit an autonomous merge, so a human retains that decision.
- The PR description for an upstream fix quotes the internal ticket. Software catches the ticket ID, and even if it didn't, a human reviews it before it goes public.

## Repeat as the design changes

Architecture changes over time, and so do models, tools and the risks you're willing to accept. Revisit the classification when any of them move. A reliable diagnostic rule might pull a function back into software. Stronger acceptance checks might let an agent own more of the loop. Automatic merging would introduce consequences that need tighter boundaries.

At the end of the day, you may find that your system belongs entirely in a prose-based skill. You may find that you don't even need an LLM at all. Or, you may find that a hybrid architecture suits the system best, whether software or an LLM owns the top-level control loop. Regardless, you'll have made deliberate architectural decisions, thought through potential failure modes and established boundaries to reduce the odds of unintentionally unleashing a swarm of rogue agents across the interwebs.

Running the same process every time also gives you and your team a shared vocabulary: which functions need judgement, what you're willing to tolerate, and who gets to propose, decide and execute. That's the conversation I've been fumbling lately. Hopefully this makes it a little easier to have.
